# 구현 검증

AGENTS.md의 시작·승인 경계를 따른다. 읽기 요청이나 기획 승인만으로 테스트를 시작하지 않는다.

1. 실제 요구사항과 현재 코드를 읽는다. 기대값은 구현 코드가 아니라 실제 과제 README·제공 자료·담당자 답에서 독립적으로 정하고 출처를 붙인다. 참가자가 확정한 가정은 그 사실과 근거를 별도로 표시한다. 해당 기능의 정상·경계·오류 사례에서 입력·기대값·실제 결과를 비교한다. 불확실한 업무 기대값은 임의로 결정하지 않는다.
2. 기존 테스트와 실행 방법을 확인한다. 과제에서 제공된 테스트와 AI가 추가한 테스트를 구분해 기록한다. AI가 만든 테스트의 통과만으로 요구사항 충족을 단정하지 않는다. 원본 데이터 변경·브라우저 저장소 덮어쓰기·외부 요청·유료 호출 등 부작용을 먼저 확인한다. 격리된 테스트 데이터와 저장 위치를 사용한다.
3. 허용된 검사를 실제 실행하고 명령·입력·출력·종료 상태를 확인한다. 테스트 파일 존재나 과거 통과 기록만으로 현재 통과라고 하지 않는다.
4. 단위/데이터/HTTP/화면 직접 조작 검사를 구분한다. 금지된 Browser/GUI 자동 조작은 하지 않는다. 참가자가 화면에서 직접 따라 할 버튼·입력값·기대 결과를 짧게 안내하며 확인 전에는 미실행으로 기록한다. 결과마다 AI 실행·참가자 직접 확인·미실행을 구분하고 참가자의 실제 확인 답이 없으면 직접 확인했다고 쓰지 않는다.
5. 실패를 재현 가능하게 보고한다. 검증만 요청받았다면 코드·업무 규칙·설정을 수정하지 않는다. 결과 문서 갱신은 허용된 경로에만 한다. 수정도 승인된 경우에만 수정 후 같은 조건과 관련 정상 흐름을 재검증한다.
6. templates/TEST_RESULTS.md를 참고해 필요한 결과 문서만 갱신한다. INDEX는 만들거나 갱신하지 않는다. 기본 결과 경로는 실제 프로젝트의 wiki/TEST_RESULTS.md이며 도구함 원본의 wiki를 덮어쓰지 않는다. 과제가 지정한 제출 경로와 AGENTS.md의 문서 갱신 허용 범위를 우선한다. 명시적인 읽기 전용 요청이면 파일은 바꾸지 않고 대화로 보고한다. PASS/FAIL/NOT RUN/BLOCKED를 구분한다. BLOCKED는 이유가 확인된 미완료 검사이며 통과가 아니다.

제출 전 검증을 요청받으면 요구사항 → 구현 위치 → 실제 검증 결과를 대조한다. 구현하지 않은 항목과 구현했지만 검증하지 않은 항목을 구분해 남은 필수·실패·미검증을 보고한다.

필수 요구 하나가 빠진 경우 일부 테스트가 통과해도 전체 완료로 보고하지 않는다. 체크할 자료가 부족하면 없는 근거를 만들어 채우지 않는다.
